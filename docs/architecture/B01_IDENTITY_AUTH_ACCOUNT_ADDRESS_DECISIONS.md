## Official-source decisions

### Identity

- Customer login identifier: **email address**.
- Email is normalized to lowercase and is unique.
- Legacy `username` from `AbstractUser` is removed in B01; `USERNAME_FIELD = "email"`.
- A dedicated `UserManager` owns user/superuser creation.
- First/last name remain profile fields.
- Phone number is not a login identifier in B01. OTP/phone verification is intentionally not invented before a real notification/provider phase.

Django officially supports using a unique email or another unique field as `USERNAME_FIELD` on a custom user model.

### Browser authentication

- Authentication mechanism: **Django database-backed session authentication** through DRF `SessionAuthentication`.
- No browser bearer token is stored in localStorage/sessionStorage.
- Login calls Django `login()`; logout calls Django `logout()`.
- Password changes call `update_session_auth_hash()` so the current session is rotated rather than silently invalidated.
- Unsafe authentication endpoints require Django CSRF protection. A dedicated CSRF bootstrap endpoint returns a token and sets the CSRF cookie.
- Production session and CSRF cookies remain Secure; the session cookie remains HttpOnly.
- Cross-origin/frontend-domain CORS and cookie-domain topology are integration/deployment concerns and must be frozen in I00/R00 rather than guessed in B01.

Django documents CSRF protection for unsafe cookie-authenticated requests; DRF authentication identifies the request while permissions separately authorize it.

### Password policy

- Registration and password change use Django password validators through `validate_password()`.
- Login errors are generic (`invalid credentials`) to avoid disclosing whether an email exists.
- Password reset/email-verification delivery is deferred until notification/provider infrastructure exists; B01 does not fake delivery.

### Permissions and ownership

- Account/profile and address endpoints require `IsAuthenticated`.
- Address querysets are always constrained by `request.user`; clients never choose an owner/user id.
- A user cannot read, update or delete another user's address by id.

### Abuse controls

- Authentication endpoints use scoped DRF throttling as an application-level abuse control.
- DRF throttling is not treated as a complete brute-force/DoS security boundary; edge/proxy controls remain required later.

### Address book

Address records are customer-owned address-book data, not shipping-eligibility authority.

Fields:
- label
- recipient_name
- recipient_phone
- country_code (two-letter code, default `IR`)
- province
- city
- postal_code
- address_line1
- address_line2
- is_default
- created_at / updated_at

Contracts:
- at most one default address per user (database conditional unique constraint);
- setting a new default clears the previous default transactionally;
- deleting the default does not guess a replacement;
- B05 owns shipping zones, delivery eligibility and checkout-address snapshots.

### API surface

Under `/api/v1/`:

- `GET /auth/csrf/`
- `POST /auth/register/`
- `POST /auth/login/`
- `POST /auth/logout/`
- `GET /account/me/`
- `PATCH /account/me/`
- `POST /account/password/`
- `GET /account/addresses/`
- `POST /account/addresses/`
- `GET /account/addresses/{id}/`
- `PATCH /account/addresses/{id}/`
- `DELETE /account/addresses/{id}/`

Email is read-only on the generic profile endpoint. A future verified email-change workflow must be explicit rather than silently changing the login identifier.
