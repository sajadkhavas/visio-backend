## Decision 1 — backend becomes public content authority

The frozen frontend currently contains editorial fixture data for guides/magazine and a client-side search surface. B08 creates durable backend content truth rather than promoting those fixtures into production authority.

`ContentEntry` owns public editorial records with explicit kind, publication state, publication time, editorial body/source/media metadata and SEO metadata.

Public APIs return only records that are:

- `status=published`;
- `published_at` is present;
- `published_at <= now()`.

Draft, archived and future-dated records fail closed and are not exposed by public list/detail APIs.

## Decision 2 — preserve frozen frontend editorial contract

The API projects backend records into the frontend concepts already frozen by F19:

- guide / magazine / policy kind;
- slug/title/excerpt;
- direct answer and audience boundary;
- author/reviewer and publication/review timestamps;
- structured body/source/media JSON;
- related guide slugs;
- SEO title/description;
- explicit `source=backend` and `authoritative=true` markers.

B08 does not wire the frontend to these endpoints. Full frontend/backend replacement of fixtures is I00 scope.

## Decision 3 — bounded PostgreSQL-backed search before a dedicated engine

The current frozen frontend needs ordinary public catalog/editorial search, filter and sort. The measured project scale does not justify Elasticsearch/OpenSearch or another distributed search service in B08.

For this phase:

- query length is bounded to 120 characters;
- unknown query parameters fail closed;
- each whitespace term is ANDed across an OR-set of approved searchable fields;
- content search uses server-maintained flattened `search_text` plus selected first-class fields;
- catalog search starts from the existing B02 public product queryset, so unpublished/future/missing-media records remain hidden;
- pagination is bounded to 48 records per page.

If later profiling proves this insufficient, the first upgrade path is PostgreSQL-native full-text search with an appropriate `SearchVector`/GIN design, following official Django/PostgreSQL guidance. `pg_trgm` may be considered for measured similarity/substring requirements. Neither is added pre-emptively.

## Decision 4 — B02/B03/B07 remain authoritative

B08 must not create a parallel commerce or payment truth.

- B02 continues to own product publication/catalog visibility.
- B03 continues to own authoritative price/inventory/reservation truth consumed by product serializers.
- B07 continues to own payment/provider/reconciliation truth.
- Content search never synthesizes client-authoritative product availability, totals or payment state.

## Decision 5 — publication integrity is enforced in PostgreSQL

The content schema enforces:

- unique `(kind, slug)`;
- published records require a publication timestamp;
- a public-query index over status/kind/publication/order fields;
- structured JSON-shape validation at the Django model boundary.

`apps/content/migrations/0001_initial.py` was generated by Django 5.2.17, not manually authored.

## Decision 6 — server-maintained search text

`ContentEntry.save()` rebuilds `search_text` from approved editorial fields so ordinary writes cannot leave stale search material.

Any future bulk import/update path that bypasses model `save()` must explicitly rebuild `search_text` or use a dedicated import service that preserves this invariant. B09 admin/import work must respect this rule.

## Decision 7 — minimal admin only

B08 registers `ContentEntry` in Django Admin to provide a minimal authoring foothold. A richer staff workflow, permissions, audit events, notifications and operational controls belong to B09.

## Decision 8 — SEO metadata is backend public data, not client truth

Each content item can carry `seo_title` and `seo_description`. API fallback is deterministic (`<title> | VISIO` and excerpt) when explicit metadata is absent.

This provides a stable SEO-supporting data contract for I00 without making frontend fixtures authoritative.

## Out of scope

B08 intentionally does not add:

- Elasticsearch/OpenSearch;
- Celery/Kafka/RabbitMQ;
- cache infrastructure without measured need;
- frontend integration;
- full editorial approval/audit workflow;
- payment/order/admin shortcuts;
- production content import from local fixtures.
