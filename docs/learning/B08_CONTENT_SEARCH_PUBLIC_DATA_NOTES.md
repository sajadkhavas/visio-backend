# B08 — Content, Search & Public Data — Engineering Notes

## Why this phase exists

The frozen frontend already exposes public guide, magazine and search surfaces, but guide/magazine content is backed by local TypeScript fixtures and search is client-side. That is acceptable for frozen presentation work, not for production authority.

B08 introduces the backend-owned public data boundary that I00 can later consume.

## What was implemented

### Public content domain

`ContentEntry` supports:

- `guide`, `magazine`, `policy` kinds;
- `draft`, `published`, `archived` states;
- publication/review dates;
- frontend-shaped editorial blocks, sources and media metadata;
- related guide slugs;
- SEO title/description;
- server-maintained flattened search text.

### Public content API

- `GET /api/v1/content/`
- `GET /api/v1/content/{kind}/{slug}/`

List supports bounded:

- `kind`;
- `q`;
- `sort`;
- page/page size.

Unknown parameters are rejected rather than silently ignored.

### Catalog search

The existing B02 product list accepts a bounded `q` parameter over approved text fields while continuing to start from `public_product_queryset()`.

This matters because search must never bypass publication, active brand/category, media or downstream commerce truth.

## Why a dedicated search engine was not introduced

The current public requirements do not prove a need for a separate service. A simple database-backed query is smaller, easier to operate and preserves the modular-monolith architecture.

The official Django/PostgreSQL path remains available if profiling later shows a need:

1. measure representative data/query latency;
2. move to PostgreSQL full-text search where appropriate;
3. add a GIN index for repeated search workloads if justified;
4. consider `pg_trgm` only for measured similarity/substring requirements;
5. consider a separate search engine only after PostgreSQL-native approaches are demonstrably insufficient.

## Publication rule

Public content is not merely `status=published`. It must also have a non-null publication timestamp that is not in the future.

This is checked in the queryset and partially protected at the database level: a published row cannot exist without `published_at`.

## Search-text maintenance rule

`search_text` is derived server data and is rebuilt during normal model saves. Future bulk update/import code must not bypass this invariant accidentally.

## Frontend integration boundary

B08 does not delete or rewrite frozen frontend fixture files. Doing so here would mix backend domain delivery with integration work and make F19 evidence harder to preserve.

I00 owns replacing the frontend fixture/search authority with these accepted APIs.

## Admin boundary

Django Admin registration is intentionally minimal. B09 owns:

- staff role/permission design;
- audited create/update/publish operations;
- notification workflows;
- richer moderation/editorial operations.

## Migration provenance

`apps/content/migrations/0001_initial.py` was generated by Django 5.2.17 in CI using `manage.py makemigrations content`. A temporary generator workflow was removed before acceptance.
