# B02 Python Learning Notes — Catalog

## Relations

Django `ForeignKey` creates a many-to-one relation and a reverse manager. B02 uses protected Brand/Category relations because deleting taxonomy that is still referenced by products should be explicit rather than destructive.

`CASCADE` is used for product-owned structures such as variants/options/media: those rows have no independent meaning after their product disappears.

## UUID identifiers

Catalog entities use `UUIDField(primary_key=True, default=uuid4)`. This gives stable public identifiers without exposing a simple sequential business count. Slugs remain the human-facing route identity.

## Validation versus database constraints

Use a database constraint when PostgreSQL can enforce the invariant directly, such as:

- one default variant per product;
- case-insensitive SKU uniqueness;
- published products requiring a publication timestamp;
- unique media positions.

Use model validation in addition to foreign keys when an invariant spans multiple rows/tables, such as confirming that a variant option and its value belong to the same product. A normal SQL `CHECK` constraint is not a substitute for a cross-table rule.

## QuerySets and Q objects

A Django QuerySet is lazy: filtering builds SQL and the query runs only when results are evaluated. `Q` objects let B02 safely compose bounded OR filters such as a comma-separated brand list without exposing arbitrary ORM field names to the client.

## select_related versus prefetch_related

`select_related` uses SQL joins and is appropriate for single-valued relations such as Product → Brand and Product → Category.

`prefetch_related` performs separate bounded queries and joins the data in Python. It is appropriate for collections such as media, options, option values, variants and badges.

DRF does not automatically optimize relation loading, so serializers must be paired with deliberate querysets. B02 has a query-count regression test to keep list serialization bounded as product count increases.

## Serializers

The B02 serializer translates normalized database rows into the frozen frontend catalog contract. The database does not need to mimic a frontend JSON object internally; normalization keeps integrity stronger while serialization gives the UI the shape it needs.

Price and inventory envelopes are intentionally serialized as non-authoritative placeholders in B02. This is an example of a contract that is structurally complete while still failing closed for business actions.

## File and storage abstraction

Django `FileField` stores a file name/path in the database. Actual bytes are handled by the configured Storage backend. B02 therefore does not hard-code a cloud provider. A later deployment phase can select local/object storage without changing the catalog domain model.

## Pagination

The product endpoint uses a dedicated `PageNumberPagination` subclass: 24 records by default and at most 48 per request. Bounding client-controlled page size protects the API from accidentally returning an unbounded catalog response.

## Migrations

The model code is the declared schema state; Django generates migration operations from the delta between model state and migration history. B02 migration files must be generated by Django 5.2.17, then the permanent CI verifies `makemigrations --check --dry-run` returns no drift and migrates an empty PostgreSQL 16.15 database from zero.

## Phase boundary

B02 teaches an important backend rule: having a field in a response does not make it authoritative. Product identity/presentation is B02 truth; price and stock remain B03 truth. The API signals this explicitly so the frontend cannot mistake incomplete commerce data for a purchasable product.
