## Accepted B03 authority

B03 makes backend pricing and inventory state authoritative at ProductVariant level while preserving B02 Product/Variant identity.

### Pricing

- canonical currency identity: `IRR`;
- authoritative catalog/storage amount: integer Toman at scale 0;
- frontend display unit: `تومان`;
- no binary float money;
- `VariantPrice.amount_toman` uses Django `DecimalField`;
- optional `compare_at_toman` uses the same exact representation;
- current price cannot be negative;
- compare-at must be null or strictly greater than current price;
- missing/inactive price fails closed;
- sale badge is derived from authoritative compare-at truth;
- provider/payment-unit conversion is deferred to B07 rather than changing B03 catalog truth.

### Inventory

- `VariantInventory` is one-to-one with a B02 ProductVariant;
- `on_hand` is stored authoritative stock quantity;
- B03 deliberately does not store a duplicate mutable `reserved` counter;
- `InventoryReservation` rows are hold truth;
- available-to-promise is derived from on-hand minus active, unexpired holds;
- availability and maximum quantity fail closed when authoritative inventory is absent/inactive or inconsistent.

### Reservation lifecycle

- UUID reservation identity;
- states: active / released / consumed / expired;
- default hold TTL: 15 minutes;
- stale active holds do not reduce authoritative availability after expiry;
- authoritative mutation paths lazily normalize stale holds;
- release is idempotent for released/expired holds;
- consumed holds cannot be released;
- consume is permitted only for active, unexpired holds;
- consume decrements on-hand exactly once;
- on-hand cannot be adjusted below active reserved quantity.

## Concurrency and oversell prevention

Critical inventory mutations use short explicit `transaction.atomic()` scopes.

The inventory row is acquired using PostgreSQL-backed `select_for_update()` before availability is checked and a reservation is created. Reservation transition paths lock inventory before the reservation row. Multi-row future operations must use deterministic ordering.

The acceptance suite contains a real transaction-capable concurrency test with two Python threads and separate Django DB connections. Starting from on-hand 5, two concurrent attempts to reserve quantity 4 yield exactly one success; authoritative remaining availability is 1 and exactly one active hold remains.

The concurrency test was never weakened or removed during B03 debugging.

## Query behavior

The public catalog queryset extends the accepted B02 prefetch plan with commerce relations:

- `select_related("price_record", "inventory_record")` for active variants;
- bounded prefetch of active inventory reservations;
- serializer projections consume prefetched state rather than introducing per-product/per-variant unbounded commerce queries.

The existing B02 query-regression contract remains in the permanent PostgreSQL test suite.

## Migration discipline and defect found

Permanent migration:

`apps/commerce/migrations/0001_initial.py`

Generated by Django 5.2.17 on 2026-09-03 and normalized only by Ruff formatting/import ordering.

It explicitly depends on:

`("catalog", "0001_initial")`

An earlier implementation head had commerce models but no commerce migration. Django therefore treated `commerce` as unmigrated during pytest test-database creation and attempted to synchronize commerce tables before the migrated catalog table existed. PostgreSQL rejected the deferred foreign key with:

`relation "catalog_productvariant" does not exist`

A temporary focused diagnostic workflow reproduced the exact failure. The test was not altered. A temporary write-enabled generator then used Django `makemigrations commerce` to create the correct initial migration. Both temporary workflows were removed before implementation acceptance.

The clean implementation head contains only the permanent read-only Backend Quality Gate.
