## Delivered domain

B07 adds durable payment attempts and reconciliation evidence, a provider contract, a concrete fail-closed ZarinPal adapter, authenticated payment creation/detail APIs and an untrusted callback entrypoint that still requires authoritative provider verification.

The implementation keeps payment/provider truth distinct from B06 Order truth. Provider verification is the only source that can produce verified payment truth. Redirect/callback status by itself never confirms an Order.

## Money and authority

- commerce-side amount: integer Toman
- provider-side amount: integer IRR
- exact conversion: `IRR = Toman × 10`
- conversion protected by PostgreSQL constraint
- payment request/verify uses the persisted server-authoritative amount
- client totals and frontend payment claims are ignored as truth

## Concurrency and idempotency

B07 enforces:

- unique Order + idempotency key;
- unique provider + non-empty authority;
- one active/verified attempt per Order;
- in-flight `requesting` rejects concurrent duplicate provider requests;
- in-flight `verifying` rejects concurrent duplicate verification;
- duplicate verified callback/reconciliation replays cannot double-consume inventory or reconfirm an Order.

## Financial truth hardening

Provider verification is committed before the B06 Order/inventory transition. If the real payment is verified but Order confirmation cannot safely complete, the payment remains `verified` and B07 records an explicit reconciliation mismatch.

Covered mismatch cases include payment after Order cancellation/expiry, reservation/inventory transition failure and server-side amount discrepancy. No mismatch silently rewrites either provider truth or Order truth.

## Provider capability audit

Current official ZarinPal Python SDK was re-checked for v4 request/verification/reversal, StartPay redirect, GraphQL refund with access token and live/sandbox base URLs. The adapter implements only those evidenced capabilities. Refund capability is config-gated and B07 exposes no unaudited customer/staff refund authorization endpoint.

## Fail-closed production configuration

Payments remain disabled by default. Enabling production payment requires provider `zarinpal`, a non-empty Merchant ID, an HTTPS callback and non-sandbox mode. Credentials/access tokens remain environment-only and are not committed to Git.
