## Implemented identity and authentication contracts

- Public customer login identifier is normalized email.
- The inherited Django `username` remains an internal opaque compatibility field and is never returned in the public account contract.
- Browser authentication uses Django database-backed sessions through DRF `SessionAuthentication`.
- Registration, login, and logout are explicitly CSRF-protected.
- A CSRF bootstrap endpoint issues the token required by the browser client.
- Login failure messages are generic for unknown email and wrong password.
- The custom email authentication backend performs a dummy password hash for an unknown email before returning failure, avoiding an obvious fast-path account-existence timing branch.
- Inactive users remain subject to Django `ModelBackend.user_can_authenticate` semantics.
- Application-level scoped throttling is configured for registration and login; it is treated as basic abuse control, not as sufficient edge/DoS protection.
- Registration runs Django password validators and atomically handles database uniqueness races.
- Password change verifies the current password, validates the replacement password, rotates the password hash, and keeps the current session valid through `update_session_auth_hash`.
- Email cannot be silently changed through the ordinary account PATCH endpoint; email change requires a later dedicated verification workflow.

## Account and address contracts

- Current-account reads and profile updates require an authenticated session.
- Account responses expose `id`, `email`, `first_name`, `last_name`, and `date_joined`; `username` is not public API state.
- Address list/detail querysets are always scoped to `request.user`.
- Address owner assignment is server-derived through `CurrentUserDefault`; client input cannot select another owner.
- Address create/update uses an atomic transaction and locks the owning user row while changing default-address state.
- PostgreSQL enforces at most one default address per user using the conditional unique constraint `accounts_one_default_address_per_user`.
- PostgreSQL also enforces case-insensitive email uniqueness using `accounts_user_email_ci_unique` over `Lower(email)` in addition to the field-level unique constraint.
- Shipping eligibility, delivery zones, and checkout address authority remain explicitly deferred to B05.

## Defects found and resolved before closure

1. Ruff initially rejected a missing `Address.__str__` and one overlong serializer line. Both were corrected before migration acceptance.
2. The first clean Meta attempt used `class Meta(AbstractUser.Meta)`, which follows Django's abstract-model Meta inheritance pattern but is not represented by the installed `django-stubs` type surface. Rather than disabling mypy or adding a blanket ignore, B01 explicitly preserves the inherited `verbose_name` and `verbose_name_plural` metadata in a normal typed `Meta` class and keeps the B01 constraint there. Django migration drift remained clean.
3. The throttle test originally tried to change `REST_FRAMEWORK.DEFAULT_THROTTLE_RATES` only through a runtime settings override. DRF's `SimpleRateThrottle.THROTTLE_RATES` is a class attribute initialized from `api_settings`; the deterministic test patches the throttle class rate mapping while leaving production settings unchanged. The resulting exact-head gate passed all 24 tests.

## Security and truth boundaries

B01 does **not** claim that DRF application throttling alone provides brute-force or denial-of-service protection. Production edge controls remain required later.

B01 does **not** implement email verification delivery, password-reset email/SMS delivery, OTP, social login, MFA, privileged-role management, audit logging, shipping eligibility, or payment identity. Those remain later-phase responsibilities.

The backend repository remains public under the B00 owner-approved visibility exception. Secret handling remains fail-closed and the permanent secret-sanity gate remains mandatory.
